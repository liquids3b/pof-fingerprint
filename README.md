# pof-fingerprint

Пассивный TCP/IP фингерпринтер с JSON API: сервис слушает входящие SYN-пакеты,
разбирает параметры стека клиента и отдаёт по HTTP примерный отпечаток ОС.

```
GET /fingerprint   ->            (в браузере: http://<ip-сервера>:8351/ — страница,
{                                  которая зовёт этот же эндпоинт и печатает JSON)
  "ip": "203.0.113.7",
  "os": "Windows",
  "os_group": "windows",
  "confidence": 0.4646,
  "coverage": 0.9011,
  "score": 16.67,
  "possible_score": 18.5,
  "margin": 9.17,
  "scores": {"Windows": 16.67, "Android": 7.5, "Linux": 3.71, "BSD": 3.5,
             "iOS": 2.25, "Mac OS": 2.25},
  "signature": "mss1460,nop,ws8,nop,nop,sackok|65535|8|1460|128|8|52|2|1|0",
  "samples": 4,
  "fingerprint": {"ip_ttl_initial": 128, "tcp_window_size": 65535, "...": "..."}
}
```

Это настоящий вывод на SYN со стека Windows (числа из `scores` — «средняя
похожесть» по каждой ОС). Тот же сервис на Linux-SYN отдаёт `"os": "Linux"` со
`score 18.65`, но `margin` всего 2.15, потому что Android и BSD используют ту
же раскладку опций — такие случаи и надо смотреть по `margin`, а не по `os`.
Apple-SYN (24 байта опций, `ws 6`) опознаётся как `os_group: "apple"` с
`coverage 0.67`; `iOS` и `Mac OS` при этом делят первое место (`margin 0.0`),
потому что профили из p0f не различают их по масштабу окна — нужен конкретный
ответ, добавьте zardaxt-профили (§ «Чужая таблица»).

Чем это отличается от [zardaxt](https://github.com/NikolaiT/zardaxt):

* **чистая стандартная библиотека** — ни pcapy, ни scapy, ни FastAPI, ни Dune
  Analytics; захват идёт через `AF_PACKET` + классический BPF, HTTP — через
  `http.server`. Установка = скопировать файлы и включить systemd;
* **своя таблица отпечатков** в JSON: собирается из собственных дампов
  (`tools/build_db.py`), дополняется конвертером чужого формата
  (`tools/import_db.py`) и правится руками;
* **скоринг за O(1) на запрос**: база компилируется в индексы
  `поле -> значение -> ОС -> вес`, поэтому запрос не зависит от размера таблицы;
* `zardaxt` — проприетарный код («Unauthorized copying ... strictly prohibited»),
  поэтому здесь **не использовано ни строки** оттуда: ни код, ни их таблица.
  Единственные внешние данные — профили Apple из `p0f.fp` под GNU LGPL, и у
  каждой такой записи в базе стоит поле `source` (см. «Чужая таблица» ниже).

## Быстрый старт

```bash
# Исходники держим вне /tmp: на части VPS /tmp смонтирован с noexec, и тогда
# ./install.sh оттуда не запускается («Permission denied (os error 13)»).
git clone <ваш-репозиторий> ~/pof-fingerprint   # или просто скопируйте каталог
cd ~/pof-fingerprint
chmod +x install.sh run.sh uninstall.sh         # zip/архив теряет бит +x
sudo ./install.sh            # /opt/pof-fingerprint + systemd + автозапуск
```

Сразу после установки сервис слушает `0.0.0.0:8351`, и страница открывается в
браузере прямо по адресу сервера — `http://<ip-сервера>:8351/` (порт установщик
открывает сам, если ufw/firewalld включён на сервере). Нужен TLS и `X-Real-IP` —
ставьте nginx-вариант, сервис тогда остаётся на `127.0.0.1`:

```bash
sudo ./install.sh --nginx      # то же плюс сниппет для nginx
sudo ./install.sh --local-only # сервис только на 127.0.0.1, публикуете сами
```

Проверка:

```bash
curl -s http://127.0.0.1:8351/health
curl -s "http://127.0.0.1:8351/fingerprint?detail=0"    # кто мы такие для сервиса
curl -s "http://<ip-сервера>:8351/health"               # отвечает ли снаружи
```

Своими руками, без установщика (отладка):

```bash
sudo python3 src/pof.py                     # захват + API
python3 src/pof.py --read dump.pcap --json  # разбор готового дампа, без root
python3 tests/test_pof.py                   # 82 теста, без сети и без root
```

## Как это работает

```
NIC ──AF_PACKET(socket)──> BPF-фильтр в ядре ──> парсер Ethernet/IP/TCP
                                                      │
                        store: {ip: [последние SYN]}   │
                                                      ▼
             таблица отпечатков (JSON) ──> скоринг по полям ──> JSON API
```

1. **Захват.** Открывается `AF_PACKET` сокет на интерфейсе основного маршрута.
   В ядро загружается программа BPF (`src/bpf.py`), которая пропускает в
   userspace только TCP-сегменты с флагом SYN и без ACK. Без фильтра Python
   получал бы каждый пакет линка — это главный источник нагрузки, поэтому
   фильтр ставится по умолчанию (`bpf: false` в конфиге его отключает).
   Пакеты с адресом отправителя, принадлежащим самому серверу, отбрасываются.
2. **Разбор.** `src/packet.py` вытаскивает только значимые поля: TTL, IP total
   length, IP ID, ToS, длину TCP-заголовка, размер окна, флаги, MSS, window
   scale, timestamps и строку TCP-опций. Все чтения проверяются по длине —
   битый или обрезанный пакет просто игнорируется.
3. **Хранилище.** `src/store.py` держит до `max_ips` адресов и до `per_ip`
   последних SYN на адрес (по умолчанию 50 000 × 3). Вытесняется самый старый.
4. **Классификация.** `src/database.py` считает похожесть SYN на записи таблицы.

### Что именно сравнивается

| Поле | Вес | Смысл |
|---|---|---|
| `tcp_options` (строка вида `mss1460,nop,ws8,nop,nop,sackok`) | 4.0 | точный набор и порядок опций |
| порядок опций (только первые буквы токенов) | 2.5 | те же опции, другие значения |
| `tcp_data_offset` (длина TCP-заголовка) | 2.5 | сколько байт занимают опции |
| `ip_total_length` | 2.5 | длина «голого» SYN |
| `ip_ttl_initial` (бакеты 32/64/128/255) | 2.0 | стартовый TTL, хопы не мешают |
| `tcp_window_size` | 2.0 | размер окна в SYN |
| `tcp_window_scaling` | 2.0 | значение window scale |
| `tcp_mss` | 1.5 | MSS |
| `ip_id_zero` | 1.5 | IP ID = 0 (характерно для Linux/DF) |
| `tcp_timestamp`, `tcp_timestamp_echo` | 1.0 + 1.0 | есть ли опция TS, что в echo |
| `ip_tos`, `tcp_flags` | 0.25 + 0.25 | ToS (ECN) и точные флаги |

Максимум — 20.5 балла. Скоринг — **средневзвешенная похожесть по сессиям**
ОС: запись с `n = 1000` весит в 1000 раз больше, чем разовый ноутбук, а
отсутствующие в SYN поля пропускаются, а не считаются промахом (в ответе это
видно как `possible_score`).

Из результата:

* `score` — средняя похожесть победителя в баллах;
* `coverage` = `score / possible_score` — насколько SYN вообще похож на что-то
  известное; ниже ~0.6 значит «стек не из таблицы»;
* `confidence` — доля победителя в сумме баллов всех ОС;
* `margin` — отрыв от второго места;
* `signature` — уникальная строка отпечатка, ей же кешируются повторы.

`Mozilla/5.0 (X11; Linux x86_64) Chrome/126` в заголовке `User-Agent` даёт
поля `user_agent_os` и `os_mismatch` — так видно подмену UA.

## API

| Маршрут | Ключ | Что отдаёт |
|---|---|---|
| `/` | нет | HTML-страница-просмотрщик: зовёт `/fingerprint` и печатает JSON |
| `/fingerprint` | нет | свой IP: отпечаток + ОС (JSON) |
| `/fingerprint?ip=1.2.3.4` | да | другой IP из памяти |
| `/fingerprint?detail=0` | нет | короткий ответ: ip, os, confidence, signature |
| `/fingerprints?limit=N` | да | все адреса в памяти, по последнему SYN |
| `/stats` | да | счётчики, размеры базы, состояние захвата |
| `/database` | да | таблица отпечатков: путь, число записей, сессии по ОС |
| `/health` | нет | liveness-проба для systemd/мониторинга |

Всё, кроме `/`, — чистый JSON: страница на `/` только зовёт `/fingerprint` и
показывает ответ, плюс поле для запроса другого IP по ключу. Скриптам HTML
разбирать не нужно.

Ключ передаётся как `?key=...`. Пока `api_key` пуст, всё открыто; установщик
генерирует случайный ключ. Ответ `404` с `"found": false` означает «этого IP
пока не видели»; `400` — «это не IP-адрес».

Если запрос пришёл с самого сервера (localhost), сервис доверяет заголовку
`X-Real-IP` (так nginx передаёт настоящий адрес клиента после терминации TLS;
бывает только при `api_host: 127.0.0.1`). Для остальных источников заголовок
игнорируется — подделать чужой IP нельзя.

CORS открыт (`Access-Control-Allow-Origin: *`), поэтому страница может звать
эндпоинт напрямую:

```html
<script>
fetch('https://pof.example.com/fingerprint?detail=0')
  .then(r => r.json())
  .then(d => console.log(d.ip, d.os, d.confidence));
</script>
```

**Важно:** смысл имеет только тот запрос, который браузер делает со своего
устройства напрямую в этот сервис. Если JSON отдаёт ваш же бэкенд (браузер →
ваш API → сервис), отпечаток будет вашего сервера, а не клиента.

## Конфиг

`config.json` (все ключи можно переопределить флагом CLI или переменной
окружения `POF_<ИМЯ_В_ВЕРХНЕМ_РЕГИСТРЕ>`):

| Ключ | По умолчанию | Значение |
|---|---|---|
| `api_host`, `api_port` | `0.0.0.0`, `8351` | адрес HTTP API: страница доступна по IP сервера; за nginx ставьте `127.0.0.1` |
| `api_key` | `""` | ключ для `/fingerprints`, `/stats`, `/database`, `?ip=` |
| `interface` | `""` | интерфейс захвата; пусто — интерфейс основного маршрута |
| `max_ips` | `50000` | сколько адресов держать в памяти |
| `per_ip` | `3` | сколько последних SYN хранить на адрес |
| `expire_seconds` | `0` | забывать адреса, которых не видно N секунд (0 — никогда) |
| `bpf` | `true` | фильтровать SYN в ядре (`false` — в Python, если VLAN/теги) |
| `ignore_local_ips` | `true` | не фингерпринтить собственные соединения сервера |
| `ignore_private_ips` | `false` | также игнорировать RFC1918/ULA |
| `database` | `database/os_fingerprints.json` | таблица отпечатков |
| `log_dir` | `log` | каталог логов; пусто — только stdout/journald |
| `verbose`, `quiet` | `false` | подробные логи / только предупреждения |

## CLI

```
python3 src/pof.py [--config FILE] [--interface eth0] [--host 0.0.0.0] [--port 8351]
                   [--api-key KEY] [--database FILE] [--max-ips N] [--per-ip N]
                   [--expire-seconds N] [--log-dir DIR] [--no-bpf] [--ignore-private]
                   [--capture-only] [--api-only] [--read FILE.pcap] [--json]
                   [--list-database] [--print-config] [--verbose] [--quiet] [--version]
```

* `--capture-only` — только захват (HTTP не поднимается);
* `--api-only` — HTTP без захвата (удобно для отладки на пустой памяти);
* `--read FILE.pcap` — офлайн-разбор дампа тем же кодом, что и живой захват;
* `--list-database` — что именно лежит в таблице, с весами.

## Установка на VPS с нуля

Рассчитано на чистый Debian 12 / Ubuntu 22.04–24.04, root или sudo.

**1. Базовая подготовка (один раз на новом сервере)**

```bash
apt update && apt upgrade -y
apt install -y python3 python3-venv curl ca-certificates
# по желанию: tcpdump для своих дампов, nginx для публикации по HTTPS
apt install -y tcpdump nginx
adduser --disabled-password --gecos "" deploy   # если хотите работать не под root
```

**2. Проверить, что SYN видны вообще**

```bash
# видим ли мы входящие SYN на своём адресе?
timeout 10 tcpdump -ni any -c 20 'tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0'
# в другом окне:  curl -s -o /dev/null http://<ip-сервера>/
```

Если пакеты видны — сервис их тоже увидит. Если пусто, значит трафик до вас не
доходит (например, между вами и интернетом стоит прокси/CDN) — фингерпринтинг
будет показывать ОС этого прокси.

**3. Установка**

```bash
# Исходники — не в /tmp: каталог вычищается при перезагрузке, а на части VPS
# /tmp ещё и смонтирован с noexec (запуск ./install.sh → «Permission denied
# (os error 13)»). Домашний каталог или /usr/local/src подходят.
git clone <ваш-репозиторий> ~/pof-fingerprint && cd ~/pof-fingerprint
chmod +x install.sh run.sh uninstall.sh   # zip/scp теряют бит +x
sudo ./install.sh            # файлы в /opt/pof-fingerprint, systemd, автозапуск
```

Если `./install.sh` всё равно не запускается, его можно выполнить через bash —
это работает и без бита +x, и на noexec-каталоге:

```bash
sudo bash install.sh         # то же самое; при noexec/без +x это единственный путь
```

Установщик: создаёт системного пользователя `pof`, копирует код и таблицу,
создаёт venv (зависимостей нет — только изоляция), генерирует `api_key`,
ставит юнит `pof-fingerprint.service` и запускает его. Сервис работает **не
под root**: в юните выданы только `CAP_NET_RAW` (для `AF_PACKET`) и
`CAP_NET_BIND_SERVICE`, плюс `ProtectSystem`, `PrivateTmp`, `NoNewPrivileges`.

Про три грабля, на которых легко потерять полчаса:

* **CRLF из Windows.** Если каталог попал на сервер через scp/архив/zip из
  Windows, строки кончаются на `\r`, и тогда `./install.sh` падает с
  `env: $'bash\r': No such file or directory`, а systemd на таком `run.sh`
  отдаёт `status=127`. Установщик вычищает CR у всего, что копирует в `/opt`
  (см. функцию `install_text`), но собственной копии он не починит: если
  `install.sh` не запускается, выполните один раз
  `sed -i 's/\r$//' install.sh run.sh uninstall.sh` (или `dos2unix *.sh`).
  В репозитории для этого лежит `.gitattributes` с `eol=lf` для скриптов.
* **`/tmp` и бит `+x`.** `sudo: cannot execute '/tmp/pof-fingerprint/install.sh':
  Permission denied (os error 13)` — это либо отсутствие `+x` после распаковки
  архива, либо `noexec` на `/tmp`. Лечится и тем, и другим: `chmod +x *.sh` и
  `sudo bash install.sh`, а сами исходники лучше держать вне `/tmp`.
* **Таблица отпечатков.** `database/mydb.pof.json` в `.gitignore`, поэтому
  после `git clone` на сервере его не окажется: сервис всё равно поднимется, но
  в логе будет `no fingerprint database at ...`, а в ответах API — `"os": null`.
  Установщик про это предупреждает; положите файл рядом с `config.json` или
  соберите его на месте (см. «Своя таблица отпечатков»).

**4. Порт 8351: доступ из браузера**

По умолчанию сервис слушает `0.0.0.0:8351` — то есть сразу после установки
страница открывается в браузере по адресу сервера:

```
http://<ip-сервера>:8351/        # ваш отпечаток; JSON — на /fingerprint
```

Порт установщик открывает сам, если на сервере включён `ufw` или `firewalld`
(`ufw allow 8351/tcp`). Если firewall у провайдера внешний (Vultr Firewall,
Security Group), правило нужно добавить в панели — изнутри сервера оно не
видно. Проверка с самого сервера и снаружи:

```bash
curl -s http://127.0.0.1:8351/health
curl -s "http://<ip-сервера>:8351/health"    # пусто/таймаут = порт закрыт
```

Заголовку `X-Real-IP` сервис доверяет только от самого сервера, поэтому
подставить чужой адрес снаружи нельзя; но `/stats`, `/fingerprints` и
`/database` открыты всем, у кого есть `api_key` из `config.json`.

**TLS/домен (nginx).** Если нужен HTTPS и реальный IP клиента после прокси,
ставьте nginx-вариант — установщик вернёт сервис на `127.0.0.1`
(`--local-only` делает то же самое):

```bash
sudo ./install.sh --nginx                    # сниппет: /etc/nginx/snippets/pof-fingerprint.conf
#   include snippets/pof-fingerprint.conf;   # внутри server{} для вашего домена
nginx -t && systemctl reload nginx

# ufw: наружу нужны только ssh/80/443, порт сервиса можно закрыть
ufw allow OpenSSH && ufw allow 'Nginx Full' && ufw --force enable
ufw delete allow 8351/tcp
```

`--nginx` и `--local-only` переписывают `api_host` в `/opt/pof-fingerprint/config.json`
на `127.0.0.1`; чтобы вернуть прямой доступ по IP, поставьте `"api_host": "0.0.0.0"`
и снова `sudo ./install.sh` (или `systemctl restart pof-fingerprint`).

**5. Проверка и обслуживание**

```bash
curl -s http://127.0.0.1:8351/health
curl -s "http://127.0.0.1:8351/fingerprint?detail=0"          # отпечаток вашего curl
KEY=$(python3 -c "import json;print(json.load(open('/opt/pof-fingerprint/config.json'))['api_key'])")
curl -s "http://127.0.0.1:8351/stats?key=$KEY"
curl -s "http://127.0.0.1:8351/fingerprints?key=$KEY"
journalctl -u pof-fingerprint -f        # логи (там же строка «страница в браузере»)
systemctl restart pof-fingerprint       # после правки config.json
```

Обновление: `git pull` в исходном каталоге (не в `/tmp`), затем снова
`sudo ./install.sh` — конфиг с ключом не перетирается (новый лежит рядом как
`config.json.new`), а старый `api_host: 127.0.0.1` установщик сам вернёт на
`0.0.0.0`, чтобы страница снова открывалась по IP.
Удаление: `sudo /opt/pof-fingerprint/uninstall.sh` (конфиг сохраняется в
`/root/pof-fingerprint-config.json`).

## Своя таблица отпечатков

Встроенная таблица — честная отправная точка: Windows 10/11, Linux 2.6–6.x,
BSD-подобные стеки, Android. Она собрана по публично известным особенностям
стеков, а не снята с реального трафика, поэтому **точность зависит от вашего
трафика**. Собственный трафик всегда точнее:

```bash
# 1. собрать SYN с машин, ОС которых вы знаете
sudo tcpdump -i eth0 -w win10.pcap 'tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0'

# 2. превратить дампы в таблицу (метка на каждый дамп)
python3 tools/build_db.py --read win10.pcap --label Windows \
                          --read ubuntu.pcap --label Linux \
                          --out database/mine.json

# 3. дописывать в неё дальше (веса складываются, не перетираются)
python3 tools/build_db.py --read ubuntu2.pcap --label Linux --out database/mine.json --merge

# 4. посмотреть, как таблица объясняет трафик
python3 tools/build_db.py --read unknown.pcap --report --database database/mine.json
```

Затем укажите таблицу в конфиге: `"database": "database/mine.json"`.
Формат — обычный JSON, ключ `n` задаёт вес записи:

```json
{
  "os": "Windows",
  "n": 40,
  "tcp_options": "mss1460,nop,ws8,nop,nop,sackok",
  "tcp_data_offset": 8,
  "ip_total_length": 52,
  "ip_ttl_initial": 128,
  "tcp_window_size": 65535,
  "tcp_window_scaling": 8,
  "tcp_mss": 1460,
  "ip_id_zero": 0,
  "tcp_timestamp": null,
  "tcp_timestamp_echo": null,
```

`null` означает «неизвестно» — поле не участвует в сравнении (так безопаснее,
чем угадывать). Тест `python3 tests/test_pof.py TestScoring.test_database_is_sane`
проверяет, что длина блока опций, `tcp_data_offset` и `ip_total_length` в записи
согласованы между собой.

### Чужая таблица: Apple из p0f и zardaxt

В стандартной поставке Apple-профили **есть** — четыре записи (`Mac OS` × 3 и
`iOS`) с полем `source: "p0f.fp (Michal Zalewski, GNU LGPL)"`. Они сконвертированы
из публичной базы [p0f](https://github.com/p0f/p0f) (`p0f.fp`, GNU LGPL), в
которой это единственный легально распространяемый источник Apple-сигнатур.
Профили старые (window scale 1–4), поэтому на живом iPhone с масштабом 5–6
сработает бонус за *порядок* опций `mss,nop,ws,nop,nop,ts,sok,eol+1`, а не
точное совпадение — `os_group` будет `apple`, `coverage` около 0.67.
Профили zardaxt как раз и добавляют свежие масштабы окон.

```bash
# конвертер понимает два формата, оба читаются из вашего файла
python3 tools/import_db.py --source p0f --file p0f.fp --os apple \
        --out database/os_fingerprints.json --merge
python3 tools/import_db.py --source zardaxt \
        --file ../zardaxt/database/newCleaned.json \
        --min-weight 3 --max-weight 50 \
        --out database/os_fingerprints.json --merge
```

* `--os` — фильтр по ОС (`apple` = `iOS` + `Mac OS`), иначе импортируется всё,
  что конвертер смог назвать;
* `--min-weight` / `--max-weight` — отсечь профили-однодневки и ограничить вес
  одного профиля; у p0f счётчиков трафика нет, поэтому там вес задаёт `--weight`
  (по умолчанию 1 — «один документированный профиль»);
* `--generic` — вместе с обычными сигнатурами брать и широкие правила `g:`
  (по умолчанию они пропускаются: у них `*` вместо значений, они только размывают
  среднее);
* `--merge` дописывает к существующей таблице; уже имеющиеся профили остаются с
  прежним весом, поэтому повторный запуск ничего не меняет (`0 new`).

**Про zardaxt.** Их `database/newCleaned.json` — проприетарная таблица
(«Unauthorized copying ... via any medium, is strictly prohibited»), поэтому она
**не входит** в этот проект и никогда не попадёт в `database/*.json` отсюда.
Конвертер работает только с вашим локальным клоном и пишет результат туда, куда
попросите: данные остаются у вас. Если ждать один только свой трафик не хочется,
это самый быстрый способ получить настоящие Apple-масштабы окна (5–6), которых в
p0f нет.

После импорта поле `source` в записи говорит, откуда она пришла, а
`--list-database` показывает вес и набор опций каждой строки.

### Проверить и подключить готовую таблицу

Если таблица уже есть (своя или чужая) — сначала проверка, потом конвертация,
потом строчка в конфиге:

```bash
# 1. что это за файл: формат, целостность, самопроверка (код выхода 0/1/2)
python3 tools/check_db.py --database database/mydb.json

# 2. конвертация в формат сервиса (скрипт печатает ровно эту команду, если видит
#    чужие имена полей: tcp_off/ip_ttl/ip_id — это zardaxt, sig/label — p0f)
python3 tools/import_db.py --source zardaxt --file database/mydb.json \
        --out database/mydb.pof.json

# 3. config.json: "database": "database/mydb.pof.json"
```

`mydb.pof.json` лежит в `.gitignore` (производная от проприетарной таблицы), так
что на сервере после `git clone` его не будет: либо повторите конвертацию там же,
либо скопируйте готовый файл в `/opt/pof-fingerprint/database/` и перезапустите
сервис (`systemctl restart pof-fingerprint`) — иначе он отвечает `"os": null`.

`check_db.py` печатает формат и счётчики, веса по ОС, список полей, которые
записи реально несут, и **самопроверку**: каждая запись классифицируется с
исключением самой себя (`leave-one-out`), поэтому `self test` показывает, сколько
профилей таблица узнаёт «вслепую», а не по подсказке самой записи. Проблемами
считаются незнакомые поля, отрицательный/нулевой вес, TTL не из бакета
(32/64/128/255), блок опций, который не может быть на проводе (не кратен 4),
`tcp_data_offset` и `ip_total_length`, противоречащие строке опций, и записи с
одинаковым профилем. Код выхода (0 — чисто, 1 — есть замечания, 2 — файл не
читается) позволяет поставить проверку в cron или CI.

Свою локальную таблицу держите вне репозитория: производные файлы от чужих
проприетарных таблиц в него не попадают (`.gitignore`, см. `database/mydb.pof.json`).

Учтите: чего нет в таблице, того нет и в ответах. В zardaxt-таблицах
(`newCleaned.json` и подобных) есть только Linux, Windows, Mac OS и iOS — меток
Android и BSD там нет, поэтому Android-клиенты будут отвечать `Linux`. Ответ при
этом честный: Android — это тот же Linux-стек (см. «Ограничения» ниже).

Дописывать к большой чужой таблице профили Android/BSD из поставляемой
(`--merge`) не стоит. Балл ОС — это среднее по её сессиям, поэтому единственная
меткая запись Android (15 сессий) перевешивает сотни записей Linux: на таблице
из 1453 записей слияние с `database/os_fingerprints.json` опускает `self test`
с 74.6% до 61.1%, и среди промахов первым идёт `Linux -> Android x186`.
Лучше оставить Android внутри Linux, как это делает сама чужая таблица, и
проверять `self test` после каждого изменения — он ловит ровно такие перекосы.

## Ограничения — что этот сервис не умеет

Честный список, чтобы не ждать лишнего:

* **Это SYN, а не вся сессия.** Фингерпринт описывает стек того, кто открыл
  TCP-соединение, и только в момент его открытия. Поведение после установки
  соединения (в т.ч. то, что делает браузер) здесь не анализируется.
* **Прокси, VPN, CDN, CGNAT** затирают исходный стек: вы увидите ОС прокси или
  промежуточного устройства. TTL-бакеты (32/64/128/255) убирают влияние числа
  хопов, но не подмену стека.
* **Android и Linux почти неразличимы** на уровне SYN — это один и тот же стек.
  Различаются они окном/масштабом, и это единственная зацепка; в ответе у обоих
  будут близкие `scores`, смотрите на `margin`.
* **Apple (iOS/macOS)** опознаётся, но грубее остальных: профили взяты из `p0f`
  (LGPL), а им больше десяти лет — они покрывают масштабы окна 1–4, тогда как у
  современных iPhone это 5–6. Отличайте Apple от остальных по `os_group: "apple"`
  и `coverage`, а точность доводите своим трафиком: `tools/build_db.py` со своими
  дампами или `tools/import_db.py --source zardaxt` (см. выше).
* **Только TCP/IP.** UDP и QUIC (HTTP/3) не фингерпринтятся.
* **NAT «съедает» IP**: адрес будет внешний для сети клиента, один на много
  устройств; в памяти сервиса будет один IP и несколько разных отпечатков
  (поэтому хранится несколько последних SYN на адрес).
* **Linux-системы не под root**: `AF_PACKET` требует `CAP_NET_RAW`. В systemd
  это выдаётся capability, при ручном запуске нужен `sudo`.
* **VLAN-теги**: фильтр BPF смотрит на ethertype без 802.1Q. На линке с
  тегированным трафиком поставьте `"bpf": false` — парсер теги понимает,
  фильтр просто не сможет до них добраться в ядре.
* **Ключ API — это не аутентификация.** Он защищает от случайного запроса к
  массовым эндпоинтам; полноценный контроль доступа — на nginx (TLS, rate
  limit, allow/deny).

## Как это устроено внутри

```
src/pof.py        CLI: режимы serve/read, потоки захвата, API и статистики
src/capture.py    AF_PACKET сокет, цикл захвата, чистка просроченных записей
src/bpf.py        ассемблер классического BPF + фильтр «SYN без ACK»
src/packet.py     разбор Ethernet/IPv4/IPv6/TCP, бакеты TTL
src/tcp_opts.py   разбор TCP-опций и каноническая строка вида mss1460,nop,ws8
src/store.py      память: {ip: [последние SYN]}, вытеснение по LRU
src/database.py   компиляция таблицы в индексы, скоринг, кеш повторов
src/api.py        JSON API на http.server (ThreadingHTTPServer)
src/netutil.py    локальные адреса, интерфейс по умолчанию, RFC1918
src/pcap.py       чтение/запись pcap для офлайна
src/log.py        логи в stdout и (опционально) в log/
tools/build_db.py своя таблица из своих дампов
tools/import_db.py конвертер чужой таблицы (p0f.fp, zardaxt newCleaned.json)
tools/check_db.py  проверка таблицы: формат, целостность, самопроверка
tests/test_pof.py 82 теста: парсер, BPF-фильтр, скоринг, API, конфиг, конвертер
```

Производительность: фильтр BPF отсекает всё до userspace, на каждый SYN приходится
один `recv` и разбор ~60 байт заголовков; классификация — 12 поисков в словаре
и кеш по `signature`. На скромном VPS (1 vCPU, 1 ГБ) это доли процента CPU при
тысячах соединений в секунду; в `/stats` есть `capture.kernel_bpf` (работает ли
фильтр в ядре), `frames` и `syns_stored`.

## Тесты

```bash
python3 tests/test_pof.py            # всё, включая HTTP-сервер на localhost
python3 tests/test_pof.py TestScoring
python3 -m unittest discover tests   # то же через discovery
```

Тесты не требуют root и интернета: SYN-пакеты собираются в памяти, оборачиваются
в pcap и проходят через тот же код, что и живой захват. Фильтр BPF проверяется
интерпретатором (`run_bpf`), который выполняет ровно те инструкции, что эмитирует
`src/bpf.py` — именно так поймалась ошибка в смещении косвенной загрузки
TCP-флагов (адрес для `BPF_IND` обязан включать 14 байт Ethernet-заголовка).
